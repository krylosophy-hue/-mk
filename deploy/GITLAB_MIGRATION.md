# Переезд сайта и CMS с GitHub во внутренний GitLab

После переезда:

- код сайта и вся история живут во внутреннем GitLab;
- редакторы входят в админку `https://moscollector.ru/admin/` своей учётной записью GitLab (если GitLab подключён к AD — доменным логином и паролем);
- каждая публикация из CMS автоматически собирается и выкладывается на сервер сайта;
- права раздаёт любой Maintainer/Owner проекта в GitLab.

Вся работа — на стороне компании. Скрипт переезда: [`deploy/migrate-to-gitlab.sh`](migrate-to-gitlab.sh), сборка и выкладка: [`.gitlab-ci.yml`](../.gitlab-ci.yml).

---

## 1. Что нужно заранее

| Что | Зачем |
|---|---|
| GitLab **16.3 или новее** | Минимальная версия, с которой работает Sveltia CMS. Проверить: Справка → «О GitLab» или `GET /api/v4/version`. |
| Проект в GitLab | Можно тот, куда сейчас клонируется репозиторий с GitHub, или новый пустой. |
| Машина для запуска скрипта | Доступ и к github.com, и к GitLab; Node.js 20+, git, curl, perl. Подходит та, где сейчас идёт клонирование. |
| GitLab Runner для проекта | Docker-executor (образ `node:20`) или shell-executor с Node.js 20 на хосте. |
| Доступ раннера к npm | К registry.npmjs.org или к внутреннему зеркалу (переменная `NPM_REGISTRY`). |
| Доступ раннера к серверу сайта | По SSH (раннер на другой машине) или раннер прямо на сервере сайта. |

**Интернет у редакторов.** Админка работает в браузере редактора и ходит в GitLab напрямую — значит, работать в ней можно из внутренней сети (из дома — через VPN). Сам скрипт Sveltia по умолчанию грузится с `unpkg.com`, а шрифты — с `cdn.jsdelivr.net`. Если у рабочих компьютеров редакторов нет интернета, см. раздел 6.

## 2. Настройки в GitLab (делает админ GitLab)

### 2.1. OAuth-приложение для входа в CMS

Admin Area → Applications (или Настройки группы → Applications) → New application:

- **Name:** `Сайт Москоллектор — CMS`
- **Redirect URI:** `https://moscollector.ru/admin/` — точно так, со слэшем в конце
- **Confidential:** снять галочку (вход идёт по PKCE, секрет не нужен — прокси авторизации тоже не нужен)
- **Scopes:** `api`

Сохранить и записать **Application ID** — это `GITLAB_APP_ID` для скрипта.

### 2.2. Права редакторов

Публикация в CMS — это коммит в ветку `main`. По умолчанию в защищённую `main` пушат только Maintainer. Варианты:

- редакторам роль **Maintainer** в проекте;
- или роль **Developer** + Settings → Repository → Protected branches → `main` → **Allowed to push and merge: Developers + Maintainers**.

Force push в `main` оставить запрещённым.

### 2.3. Переменные CI/CD

Settings → CI/CD → Variables:

| Переменная | Значение | Когда |
|---|---|---|
| `DEPLOY_PATH` | каталог сайта, например `/var/www/moscollector/dist` | всегда (без неё выкладки нет, только сборка) |
| `DEPLOY_HOST` | сервер сайта | если раннер не на сервере сайта |
| `DEPLOY_USER` | пользователь SSH | вместе с `DEPLOY_HOST` |
| `SSH_PRIVATE_KEY` | приватный ключ, **тип File**, Protected | вместе с `DEPLOY_HOST` |
| `SSH_KNOWN_HOSTS` | вывод `ssh-keyscan <сервер сайта>` | вместе с `DEPLOY_HOST` |
| `NPM_REGISTRY` | адрес внутреннего зеркала npm | если нет доступа к registry.npmjs.org |

Выкладка подменяет каталог целиком: новая версия распаковывается в `DEPLOY_PATH.new`, затем каталоги меняются местами переименованием. Предыдущая версия остаётся в `DEPLOY_PATH.prev` — откат: поменять каталоги местами обратно. Пользователю `DEPLOY_USER` нужны права на запись в каталог, **родительский** для `DEPLOY_PATH`.

### 2.4. Мониторинг (по желанию)

CI/CD → Schedules → New schedule, например `0 9,21 * * *`. Пайплайн по расписанию проверяет, что сайт отвечает, и что до окончания TLS-сертификата больше 21 дня. При провале GitLab пришлёт письмо владельцу расписания.

## 3. Переезд

1. **Остановить синхронизацию GitHub → GitLab** (cron, скрипт или pull mirror — что сейчас используется). Иначе после переезда она будет конфликтовать с правками из CMS.
2. Сухой прогон — всё готовит и проверяет, ничего не отправляет:

   ```bash
   GITLAB_URL=https://git.example.local \
   GITLAB_PROJECT=web/moscollector-site \
   GITLAB_APP_ID=<Application ID из п. 2.1> \
   GITLAB_TOKEN=<личный токен GitLab, scope read_api> \
   ./deploy/migrate-to-gitlab.sh
   ```

   Скрипт проверит версию GitLab и проект, склонирует `main` с GitHub, переключит CMS на GitLab, соберёт сайт и сделает коммит в рабочей папке `mk-gitlab-migration/repo`. Если во внутреннем `main` уже есть коммиты, которых нет на GitHub, скрипт остановится и ничего не тронет.
3. Посмотреть изменения: `git -C mk-gitlab-migration/repo show`.
4. Отправить: тот же запуск с флагом `--push`. Отправка обычная, без force: история сохраняется целиком.

## 4. После переезда

1. Пайплайн `build → deploy` прошёл (Build → Pipelines), сайт обновился.
2. Применить CSP админки на сервере сайта: скрипт уже вписал адрес GitLab в `deploy/nginx-moscollector.conf` (блок `location /admin/`). Если nginx-конфиг сервера ведётся отдельно — перенести оттуда строку `Content-Security-Policy` этого блока.
3. Из внутренней сети открыть `https://moscollector.ru/admin/` → **«Войти через GitLab»** → разрешить доступ приложению. Проверить: открыть новость, сохранить без изменений или с мелкой правкой → в GitLab появился коммит → пайплайн выложил изменение.
4. Запасной вход без OAuth: «Войти с помощью токена доступа» — личный токен GitLab со scope `api`.
5. Репозиторий на GitHub перевести в архив (Settings → Archive), чтобы никто не публиковал через старую админку. GitHub Pages перестанет быть актуальным — это ожидаемо.

## 5. Откат

Пока GitHub-репозиторий не в архиве, откат — просто продолжить работать через GitHub и вернуть синхронизацию. Во внутреннем GitLab коммит переезда отменяется обычным `git revert`.

## 6. Если у компьютеров редакторов нет интернета

Запуск скрипта с флагом `--vendor-cms` кладёт скрипт Sveltia CMS и его подгружаемые части в сам сайт — `public/admin/sveltia/` (около 6 МБ), версия записана в `VERSION`. Админка перестаёт зависеть от `unpkg.com` в основной работе, и её версия больше не меняется сама.

Проверено с полностью запрещёнными внешними CDN: админка запускается, вход через GitLab доступен. Но два ресурса Sveltia всё равно берёт из интернета:

- **шрифты и иконки** с `cdn.jsdelivr.net` — без них текст будет системным шрифтом, а на месте иконок в редакторе появятся слова (`arrow_back`, `delete` и т. п.). Работать можно, но неудобно;
- проверку новой версии с `unpkg.com` — без неё ничего не ломается.

Поэтому вариант `--vendor-cms` подходит, если интернет у редакторов есть, но ограничен (например, закрыт `unpkg.com`). Если интернета нет совсем — нужна сборка CMS из npm-пакета вместе с сайтом, это отдельная доработка, обращайтесь к разработчику сайта.

Обновление локальной копии — раз в месяц (Sveltia регулярно выпускает исправления безопасности): внутри GitLab взять свежий `@sveltia/cms` через `npm pack` и заменить содержимое `public/admin/sveltia/`, как это делает скрипт в шаге 4c.
